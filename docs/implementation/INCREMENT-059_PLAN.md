## Problem
A job's immutable `snapshot.assetIds` identifies asset ordering, while durable `device_stage_transfers` tracks a separately numbered owned path, pinned byte readback and optional MediaStore row. The operator review now reports stage/audit history but lacks a coherent index-by-index proof that the *Nth frozen asset* maps to the *Nth durable stage* and a unique indexed MediaStore row. Duplicate local basenames, an extra/missing stage, an aliased row ID or tampering can make naive "select first matching thumbnail" unsafe. A persisted row is NOT current picker selection proof, and no runnable selection should be inferred.

## Detailed implementation
1. `packages/contracts/src/schedule.ts`: introduce `PersistedOrderedMediaReport` with redacted 0–32 ordered media slots (ordinal, IMAGE/VIDEO/UNKNOWN, evidence state, finite blocker codes). Global status `BLOCKED`/`INDEXED_CANDIDATES_NOT_PICKER_VERIFIED`/`NO_MEDIA`, `scope:'PERSISTED_STAGE_ORDER_NOT_PICKER_VERIFIED'`, `canSelect:false`, `canDispatch:false`; never expose asset/stage IDs, MediaStore row IDs, file/remote paths, filenames, hash, nonce or phone serial. Add to existing `JobStageReviewPage`, preserving response shape and reconciliation pagination.
2. New `packages/database/src/media-selection.ts`: pure source algorithm `assessPersistedMediaOrder` using immutable job snapshot + stage records + historical claim generation and effect-presence bit. Order is ALWAYS `snapshot.assetIds`, never SQLite stage insertion order, filename, thumbnail or MediaStore provider iteration. Each ordered slot must have unique pinned READY asset ID/hash/bytes/kind, one stage exactly at that ordinal, same job/device/snapshot/claim generation and pinned hash+bytes/assetId, the canonical owned target from pinned extension and ledger nonce, a successful exact remote-byte readback, an immutable matched MediaStore row with exact canonical `display_name`/`relative_path`/`bytes`/mime family and a numeric row ID. Extra/missing/duplicate stages, row-ID or path alias across slots, tampered owner/path, wrong claim generation, effects, unknown app state and malformed pinned media all fail closed. Every result remains non-selectable and non-dispatchable even if all persisted evidence is present.
3. `packages/database/src/index.ts`: integrate read-only algorithm in existing `jobStageReview(jobId,cursor?)` by fetching frozen validated snapshot, bounded <=33 stage IDs, historical claim generation and existence of external effects. No migration, DB mutation, lease acquisition, ADB, MediaStore query or new public command. Existing cursor scope and redaction preserved.
4. `apps/desktop/src/renderer/JobStageReviewDialog.tsx`: accessible `Thứ tự media đã lưu (chưa xác minh picker)` section with ordinal, image/video, evidence/blocker explanations, empty/no-media status, and explicit "chưa được chọn trong picker/không được phép đăng". No click-to-select, deletion, retry, source token, provider input or automatic probe.
5. `packages/database/src/media-selection.test.ts`: pure multiple-media cases with same original basename, correct order by asset ID regardless of stage input order, unique ordinal-generated target and MediaStore rows; wrong per-ordinal hash, swapped ordinal, malicious remote path, duplicate/aliased row ID, missing/extra stage, no claim, wrong job/snapshot, bad MIME/relative path, no readback and external effect all BLOCKED. `packages/database/src/device-stage.test.ts`: real SQLite test with one indexed stage and explicit read-only redaction, unindexed/missing stage blockers, no stage/job/effect mutation after call and restart. `tests/ui/schedule.spec.ts`: verify UI message and no secret leak and no select/post actions.
6. Exact SHA GitHub CI: generated contracts, typecheck, lint, build, unit/integration, Chromium UI, Windows VerifyOnly, plan validators; fix failures and rerun. Update `INCREMENT-059_RESULTS.md`, `PROGRESS.md`, `COMPLETION_PLAN.md`, checkpoint-052 only with verified SHA/OS evidence.

## State transitions and failure cases
No state transition in this increment: `NEEDS_REVIEW` stays, stage remains unverified, no new claim/effect or remote operation. `INDEXED_CANDIDATES_NOT_PICKER_VERIFIED` means only past durable owner/byte/row identities are internally consistent, never Android picker proof and never `canSelect`/`canDispatch`. The absence of a MediaStore row or any ambiguity stops before picker operations. Text-only jobs yield `NO_MEDIA` without an implied authorization. Malformed frozen identity is BLOCKED with a bounded code, not treated as empty selection.
